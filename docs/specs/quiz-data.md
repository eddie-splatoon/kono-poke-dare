# 問題データの形式と検証

## 概要

問題データをゲームロジックから分離して、静的ファイルとして配信する。データの形式、ヒントの書き方、配信方法を定め、機械的に確かめられる項目を CI で検証する。

## 要件

| ID   | 要件                                                                                     |
| ---- | ---------------------------------------------------------------------------------------- |
| R-1  | 形式を満たす問題は、問題点が 0 件になる                                                  |
| R-2  | オブジェクトでない値は問題点になる                                                       |
| R-3  | `number` が 1 以上の整数でなければ問題点になる                                           |
| R-4  | `name` が文字列でなければ問題点になる                                                    |
| R-5  | 正規化して空になる `name` は問題点になる                                                 |
| R-6  | `aliases` が文字列の配列でなければ問題点になる                                           |
| R-7  | 正規化して空になる別名は問題点になる                                                     |
| R-8  | `hints` が文字列の配列でなければ問題点になる                                             |
| R-9  | 正規化して空になるヒントは問題点になる                                                   |
| R-10 | ヒントが 10 個でなければ問題点になる                                                     |
| R-11 | 同じ問題の中で、正規化して同じになるヒントは問題点になる                                 |
| R-12 | 別の問題と同じ文のヒントは問題点にならない                                               |
| R-13 | ヒントに `name` が含まれると問題点になる(ひらがなとカタカナの違いを同じものとして扱う) |
| R-14 | ヒントに別名が含まれると問題点になる                                                     |
| R-15 | 正規化して `name` または別の別名と同じになる別名は問題点になる                           |
| R-16 | 問題点は最初の 1 件で止めず、すべて返す                                                  |
| R-17 | 問題点のメッセージに問題番号を含める                                                     |
| R-18 | 問題番号の一覧が 1〜期待する問題数で揃っていれば、問題点が 0 件になる                    |
| R-19 | 欠番は問題点になる                                                                       |
| R-20 | 範囲外の問題番号と、重複した問題番号は問題点になる                                     |
| R-21 | `index.json` の `count` が 1 以上の整数でなければ問題点になる                            |
| R-22 | `count()` は `index.json` の問題数を返す                                                 |
| R-23 | `count()` の結果を再利用し、`index.json` を 2 回取得しない                               |
| R-24 | `findByNumber` は番号を 4 桁にしたファイルを `baseUrl` の下から取得して返す              |
| R-25 | `findByNumber` は、整数でない番号と範囲外の番号では問題のファイルを取得せず `null` を返す |
| R-26 | `findByNumber` は、問題のファイルが 404 なら `null` を返す                               |
| R-27 | 検証を通らない応答と、JSON として読めない応答は `InvalidQuestionDataError` にする        |
| R-28 | ファイルの番号と `number` が異なる応答は `InvalidQuestionDataError` にする               |
| R-29 | 問題のファイルの 404 以外の HTTP エラーと、`index.json` の HTTP エラーは `QuestionDataFetchError` にする |
| R-30 | 配信するデータで、ゲームの開始、回答、10 個で終了までを実行できる                        |
| R-31 | 配信するデータの検証で、問題点が 0 件になる                                              |
| R-32 | ディレクトリの検証は、形式を満たさない問題のファイルを検出する                           |
| R-33 | ディレクトリの検証は、欠番と余分なファイルを検出する                                     |
| R-34 | ディレクトリの検証は、JSON として読めないファイルを検出する                              |
| R-35 | ディレクトリの検証は、ファイル名と `number` の不一致を検出する                           |
| R-36 | ディレクトリの検証は、`count` と期待する問題数の不一致を検出する                         |
| R-37 | `fetch` を `this` なしで呼び出す(ブラウザの `fetch` は別の `this` で呼ぶと失敗する)       |

## ドメインルール

### 姿違い

- 種族で 1 問とする。姿ごとに問題を分けない
- 姿違いには終盤のヒント(8〜10)で触れる
- 姿の名前は `aliases` に入れて正解にする。種族として合っている回答を不正解にしないためである

### ヒントの難易度の順序

1 が最も難しく、10 が最も易しい。順序は機械的に確かめられないので、抽出して読んで確認する。

| ヒント | 内容                                                               |
| ------ | ------------------------------------------------------------------ |
| 1〜2   | 多くの種族に当てはまる周辺的な特徴(能力の傾向、覚える技の傾向など) |
| 3〜4   | 大きさ、重さ、生息する環境など、候補を絞る事実                     |
| 5〜6   | 登場した世代、性格や生態、見た目の一部                             |
| 7〜8   | タイプ、進化の関係                                                 |
| 9〜10  | 姿違い、代表的な外見、名前の文字数や頭文字など、ほぼ特定できる情報 |

### 書き方の基準

- 独自の文章で書く。図鑑の説明文を転載しない
- 公式の画像、ロゴ、音声を使わない
- 確かめられる事実だけを書く。タイプや進化などは、信頼できるデータと照合する
- 正解の名前と別名を含めない
- 1 文で書き、文末を「である」調にそろえる

### 重複と混入の判定

- ヒントの重複は、同じ問題の中だけで判定する。タイプなどの事実は、別の問題と同じ文になることがある
- 比較には回答と同じ正規化(`normalizeAnswer`、`docs/specs/game-rules.md`)を使う
- 名前の混入は部分一致で判定する。短い名前が別の語の一部として一致したときは、文を書き換えて解消する

### 配信方法

全データを 1 度に配信しないように、1 問を 1 ファイルにする。遊ぶ日の 1 問と問題数だけを取得すれば済む。`public/` は静的書き出しにそのまま含まれるので、ビルド処理を増やさない。

問題番号は 1〜問題数の連番とする(`questionNumberForDay` が返す範囲)。

### 全種類の確認

`scripts/check-question-data.test.ts` の `EXPECTED_QUESTION_COUNT` を期待する問題数とする。サンプルの間は 6 にして、全種類のデータの完成時(#16)に 1025 にする。

## 入出力

### ファイル

| パス                                | 内容                     |
| ----------------------------------- | ------------------------ |
| `public/data/questions/index.json`  | `{ "count": 問題数 }`    |
| `public/data/questions/NNNN.json`   | 1 問のデータ(`0001.json`) |

問題のファイルの項目は次のとおりである(`Question`)。

| 項目      | 型         | 範囲                                     |
| --------- | ---------- | ---------------------------------------- |
| `number`  | `number`   | 1〜問題数の整数。ファイル名の番号と同じ  |
| `name`    | `string`   | 正解として表示する名前                   |
| `aliases` | `string[]` | `name` のほかに正解とする名前。空でもよい |
| `hints`   | `string[]` | 難しい順のヒント 10 個                   |

架空の例を示す。

```json
{
  "number": 1,
  "name": "カセツモン",
  "aliases": ["メガカセツモン"],
  "hints": ["ヒント 1 の本文", "…", "ヒント 10 の本文"]
}
```

### 関数

| 関数                                        | 入力                         | 出力                        |
| ------------------------------------------- | ---------------------------- | --------------------------- |
| `validateQuestion`                          | `unknown`                    | 問題点の `string[]`         |
| `validateQuestionManifest`                  | `unknown`                    | 問題点の `string[]`         |
| `validateQuestionSet`                       | 問題番号の配列、期待する問題数 | 問題点の `string[]`         |
| `createStaticQuestionRepository`            | `baseUrl`、`fetch`           | `QuestionRepository`        |
| `checkQuestionData`(テストから使う)         | ディレクトリ、期待する問題数 | 問題点の `string[]`         |

`baseUrl` は `basePath` を含み、末尾に `/` を付けない(例: `/kono-poke-dare/data/questions`)。

## エラー

| エラー                     | 条件                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| `InvalidQuestionDataError` | 応答が JSON として読めない、検証を通らない、ファイルの番号と一致しない |
| `QuestionDataFetchError`   | 問題のファイルの 404 以外の HTTP エラー、`index.json` の HTTP エラー  |

通信そのものの失敗は、`fetch` の例外をそのまま伝える。いずれの場合も、ゲームの状態を進めない。

## セキュリティ

- 配信データの応答を信頼しない。内側へ渡す前に検証する
- `questionNumber` は端末内のデータから来ることがあるので信頼しない。1〜問題数の整数だけをファイル名にする
- 同じオリジンの静的ファイルを取得するだけで、外部へデータを送信しない
- 配信データから正解を読めることは許容する(`security.md`)
