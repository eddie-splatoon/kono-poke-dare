# 機能仕様のドキュメント

機能の仕様を `docs/specs/` に記録する。人と AI が、コードを読まなくても、何が正しい振る舞いなのかを判断できるようにする。

## 規則

- 実装の前に、`docs/specs/README.md` の索引から該当する仕様を探して読む
- 機能の実装や変更と同じ PR で仕様を更新する。コードと仕様が食い違う状態でマージしない
- 1 機能 1 ファイルにする(`docs/specs/<feature>.md`)。ファイル名は英小文字のケバブケースにする
- 新しい仕様は `docs/specs/_template.md` をコピーして作り、索引に追記する
- 正解データそのものや秘密情報を書かない

## AI が読み取れる形式

決まった形式で書く。

- YAML frontmatter に、状態と、Issue、コード、テストへの参照を書く
- テンプレートの見出しを変えない。該当しない節には「なし」と書く
- 要件に `R-1`、`R-2` と番号を振る。番号は再利用しない。廃止した要件は、番号を残して廃止と書く
- 1 つの要件には、テストで確かめられることを 1 つだけ書く
- 曖昧な表現(「適切に」「なるべく」など)を使わない

## frontmatter

| キー      | 内容                                                         |
| --------- | ------------------------------------------------------------ |
| `title`   | 機能の名前                                                   |
| `status`  | `draft`(実装前)、`implemented`(実装済み)、`deprecated`(廃止) |
| `issues`  | 関連する Issue の番号の配列                                  |
| `code`    | 実装のパスの配列                                             |
| `tests`   | テストのパスの配列                                           |
| `updated` | 最終更新日(`YYYY-MM-DD`)                                     |

## テストとの対応

テスト名を要件 ID で始める。ID で検索すれば、要件とテストの間を行き来できる。

```sh
grep -rn "R-1:" src
```

ID は仕様のファイルごとに振るので、検索するときは `tests` のパスと合わせて確認する。
