# テスト駆動開発

## 手順

1. **Red**: 仕様の要件を確かめるテストを書き、期待どおりの理由で失敗することを確認する
2. **Green**: テストが通る最小の実装を書く
3. **Refactor**: テストが通る状態を保って、重複や名前を整理する

- テストのない実装を先に書かない
- バグ修正は、バグを再現して失敗するテストから始める
- 動作を変えないリファクタリングでは、既存のテストが通り続けることを確認する。足りなければ先にテストを足す
- 失敗したテストを、通すために消したり緩めたりしない。仕様が変わったときは、先に仕様を更新する

## 層ごとの方針

| 層                   | 方法                          | 外部の扱い                                                                   |
| -------------------- | ----------------------------- | ---------------------------------------------------------------------------- |
| `domain`             | Vitest の単体テスト           | モックを使わない                                                             |
| `application`        | Vitest の単体テスト           | ポートをインメモリの fake に差し替える                                       |
| `infrastructure`     | 統合テスト                    | IndexedDB の実物に近い環境で確認する。日付キーの重複防止と、不正な保存値の扱いもここで確かめる |
| `app` / `components` | Playwright で主要な操作を確認 | ロジックは内側の層に置き、ここには持たせない                                 |

Playwright はまだ導入していない(#1 の残作業)。導入までは、画面の確認結果を PR の「動作確認」に書く。

## テストの書き方

- テストは対象の隣に `*.test.ts` で置く
- テスト名は、仕様の要件 ID で始めて、確かめる振る舞いを日本語で書く

```ts
it("R-1: ヒントが進むごとに 100 から 10 ずつ下がる", () => {
  // ...
});
```

- 実装の詳細ではなく、振る舞いを確かめる
- 境界値と異常系を書く
- 時刻や乱数を固定し、実行するたびに結果が変わらないようにする
